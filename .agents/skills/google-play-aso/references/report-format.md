# 逐项目交付

每个已确认的发行 App 输出两份文件，命名为包名、locale、“数据分析”或“ASO优化方案”及日期，存在时加数字后缀。不同 App 不共享统计结果；未确定包名的本地准备分析使用项目名，明确无 Play 数据。

## 数据分析报告

1. 分析范围与数据源：项目与发行包映射、时间、locale、请求周期、各来源状态及覆盖范围。
2. 项目事实：主要真实能力及相对源码依据；标明尚未验证/计划/演示，与当前商店声明不一致的地方。
3. 当前商店资料：完整原文标题、简短说明、详细说明及字符数；缺失字段明确缺失，不翻译冒充原文。
4. 评分与评价：整体评分与样本均分分别展示；匿名概括主题，明确样本量。
5. 安装与卸载、崩溃与 ANR、商店访问与获客：各附实际周期、覆盖度与缺失项；没有来源不填零。
6. 数据结论与限制：事实结论可回溯到上文，不包含建议文案，不归因未经验证的因果关系。

## ASO 优化方案

按“当前信息 → 修改说明 → 修改后信息 → 验证计划”组织。

- 当前信息：项目/包名/抓取时间、locale 及 requested/configured_default/fallback，完整当前文案和有效证据。
- 修改说明：分别说明标题、简短和详细说明改不改、为什么、源码与数据依据。保留不改字段的理由；将可读性假设和真实搜索表现区分。
- 修改后信息：完整输出三项建议文案，含未改字段；保留源商店语言，除非用户要求本地化。显示 validate-copy 检查的字符数和 30/80/4000 目标上限，以控制台实际校验为准；母语/法律审校未完成须标记。
- 验证计划：明确每个关键假设需要的证据和比较周期；覆盖不足时先补证据，不承诺改文案就能解决卸载、稳定性或留存问题。

没有当前商店文案时，不伪造“修改前”；将建议明确标为基于已实现能力的上架准备稿。没有足够产品依据时列出待确认内容，不能补造功能凑满字段。

多项目最后汇总已分析、部分数据可用、仅本地准备及受阻情况，并给出逐 App 文件链接；没有执行真实 API 时不要写成远端验证通过。


## 交付前核对

以本次 JSON 的 packageName、locale、analysisDays 和 fetchedAt 核对两份报告，并记录源码提交及未提交状态。在线结果以本轮 manifest.json 的 results 中 evidenceFile/dataReport 对应关系为准，并核对 runId；文件已按包名/locale 分目录。保留原数据基础稿，最终核对版另存，不覆盖原证据。离线导入使用 importedAt、输入哈希和 summary.window，不把导入时间当抓取时间，也不为无语言维度的统计填写 locale。

文案 JSON 与最终优化方案必须一致；任何后续文字修改需要重新执行本地文案校验。只有当前字段原文取得且产品能力核实后，才能标为有依据的前后对照；未取得原文时标上架准备稿。
