# UI 风格与一致性审查

负责约束和检查，设计方案由 ui-design 主导。读取目标项目实际存在的风格规则、资源索引、任务设计和受影响画面；DevLib 工作台使用 [风格规则](../../rules/ui-style.md) 与 [基线](../../config/ui-baseline.md)。其他目标项目使用其自身规范，缺失时从实际资料提出暂定约束并标注假设，不继承 DevLib 的工作台品牌、配色或导航。

## 审查步骤

1. 确认用户指定稿、设计目标与当前实现分别是什么，旧页面和未认可截图不能自动升级成目标。
2. 设计阶段核对语义颜色、文字层级、间距、组件、图标、密度和主次操作；只处理受影响区域。检查风格调整是否导致功能入口丢失、名称改变或操作绕路，将流程问题交给主执行者统一解决。
3. 实现阶段核对真实资源绑定和有效样式，再对照同版本、同状态的实际画面。检查相关明暗、长文案、字体与窗口变化；未覆盖项列明，不宣称通过。
4. 每项输出位置、规则来源、证据、用户影响及具体修复。区分项目约束、平台要求、主观建议和未知项；数值需要真实来源。
5. 复用同一设计交接与问题清单。已授权实现时由主执行者修复并复核；仅审查时不修改产品。不重复调用设计或实现 Skill 形成循环。

## Apple 设计参考的角色

Apple 的清晰层级、内容优先、反馈和无障碍原则可作为审查依据，不决定 Android 的导航、单位、触控约定或组件。项目已有 [HIG 索引](../ui-design/references/hig-lookup.md) 与 [跨平台边界](../ui-design/references/cross-platform.md)，按实际问题选读，引用前读原文，历史快照不代表当前官方要求。

用户明确调用 apple-design 时使用可用安装版本，将发现合并到本次问题清单；不再生成竞争设计方案或复制另一份 token 表。不为此新增项目内同名副本，外部 Skill 缺失时如实说明。一般风格检查使用本能力及已有参考即可。

## 交付

给出“方案约束检查 / 源码一致性 / 实际视觉”的独立结论，以及必要的例外、剩余问题和证据链接。功能完整性由需求验收核对，操作流程由旅程审查核对，构建由平台工作流验证。风格通过不代表功能完成或用户认可。

维护后按 [行为案例](../ui-design/references/evaluation-cases.md) 推演边界；人工推演与真实任务效果分开报告。
