# 需求澄清

承担需求分析职责，交付可实施的任务说明。读取目标项目的适用规则、相关源码或已有材料；区分用户明确要求、已核实事实和暂定假设，不从角色身份推导额外需求。

## 方法

1. 判断使用者及其目标。库任务关注消费开发者的接入与调用；Demo 任务关注能力发现和体验；消费产品以其真实用户为准。
2. 沿一个具体场景描述当前障碍和期望结果。“优化”可能指视觉、步骤、可靠性或性能，先结合上下文定位，不能默认全部重做。
3. 查找已有实现、设计参考及约束，界定本轮范围与不处理项。不要把 DevLib 的模块、包名、业务边界照搬到其他项目。
4. 仅对会改变核心行为、范围或不可逆决策的缺失信息提问，优先给出推荐选择与理由。已回答的问题不重复问；可逆实现细节采用明确假设继续，等待关键答案期间推进不依赖答案的工作。
5. 写可观察的验收条件：在什么前提下，执行什么操作，应出现什么结果，以及如何验证。优先覆盖主路径和本次涉及的失败/边界路径，不凭空添加功能或性能数字。

## 交付与交接

用短段落或紧凑清单给出：目标用户与场景、当前问题、期望行为、范围、事实/假设、验收条件及验证方式。简单任务在对话中说明即可；复杂任务或用户要求时再保存任务文档。

- 视觉需求缺少参考时，说明暂定视觉方向，交给 $ui-design 形成具体方案；已有设计稿或任务卡保留其来源与版本，不另建重复需求。“高级、好看”需转换为可观察的层级、密度或一致性目标。
- 已获实现授权且无关键阻塞时，交接到现有实现能力并继续完成；用户只要求分析时止于分析，不额外设立全量审批步骤。
- 新反馈更新同一任务说明和验收条件，保留原目标，避免维护互相矛盾的多份需求。
- Skill 提供分析方法，不代表已创建独立产品智能体，也不自动授权委派。
