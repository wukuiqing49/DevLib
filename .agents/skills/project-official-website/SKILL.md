# 从项目代码与资源创建官网

在 DevLib 中以本项目 `.agents/skills/project-official-website/` 为准，不混用个人目录的同名旧副本。

交付可运行的网站文件，而不是只提供策划或要求用户先整理功能表。项目路径是主要输入；自行分析技术栈、产品定位和现有素材，按用户指定的语言和视觉方向实现。

## 确定源项目与输出

- 读取目标项目适用的 AGENTS.md 和局部规则，检查 Git 状态，确认用户已有修改。
- 明确区分源项目与官网输出。用户给定输出目录时优先使用；未指定时，有现成独立官网目录则沿用，否则使用源项目内未占用的 `website/` 作为官网工作区。源项目本身已是网站时，不盲目重建覆盖，按官网任务确定修改范围。
- 分析阶段只读源项目。不要修改 App、业务代码或构建配置来配合宣传内容。官网适配写入输出目录，原有人工内容和未提交修改应保留。
- 缺少目录时询问项目路径；只有产品选择确实影响实现时才询问，例如多个互不相关的应用入口。未知域名、邮箱、商店链接不是生成草稿的阻塞项。

## 从实现提取产品事实

读取 [references/source-evidence.md](references/source-evidence.md)，按实际技术栈定位入口、用户流程、功能实现与资源。不要仅把 README、依赖清单或权限当作已实现功能。

新建静态官网使用 `<workspace>/public/` 存放可部署文件，`<workspace>/.site-audit/` 存放审计记录；只预览和部署 public。已有框架沿用其构建输出目录，审计目录必须在部署根之外。用户明确指定根目录入口时按其要求实现，将审计记录放在另一个不被发布的目录。

读取 [references/site-records.md](references/site-records.md)，在审计目录维护 `project-facts.json`，至少记录：产品名称、类型、版本、源语言、目标用户、功能事实、代码证据相对路径、所选图片与来源、可确认链接、未知项和不得宣称的内容。分析时间与产品版本分别记录。将定位或受众推断明确标记为推断。

核查每个准备宣传的功能是否在当前选择的产品/变体中可达。未接入、仅测试、废弃或条件关闭的代码不能作为当前功能宣传。依赖 SDK 不等于产品提供该能力。开发库官网应呈现 API 能力、接入与代码例子，不把演示 App 当成消费级产品。

## 选择资源与视觉方向

读取 [references/design-and-refresh.md](references/design-and-refresh.md)，先根据品牌和素材确定视觉方向；更新已有官网时检查文件归属和哈希，保留人工改动。

- 优先用户指定的资源，其次项目内当前产品的图标、截图、录屏、设计资产。实际查看候选图片，核对产品身份、内容、比例与可用性，再复制必要公开资源。
- 没有截图时，可以继续制作文字、图标与真实代码示例驱动的官网；说明素材缺口，不伪造截图、客户案例、评分、用户量或性能数据。源码中有演示图不代表适合对外使用。
- 根据品牌和产品用途选择布局、字体、色彩与信息密度；复用现有设计体系，避免把当前示例产品的配色和模板写成所有官网的规则。
- 使用可用的设计或图片 Skill 仅作为辅助，不使本 Skill 必须依赖其他 Skill 才能完成。

## 创建网站

- 已有官网框架时沿用；新建默认语义化 HTML、CSS 和少量 JavaScript，可直接静态托管。只有需求确实需要时才增加框架或构建依赖，不引入无关后台、数据库、账号或支付系统。
- 首页清楚呈现产品用途、核心价值、已验证功能、真实资源和主要操作入口。页面数量按内容决定，不机械生成博客和大量功能页。
- App 官网主要操作是已确认的下载或商店入口；库项目是接入文档、示例和源码入口。未知链接不写成可点击的占位地址。
- 独立功能页要有真实流程和足够信息；隐私、定价、支持等内容来自明确证据。缺少法律信息时列入待确认，不依据代码自动承诺法律条款。
- 仅生成用户要求或项目明确需要的语言。品牌、包名、API、URL 保持准确；未审核翻译注明草稿。多语言页面设置正确 lang/dir 和等价页面跳转。
- 使用确认的公开域名生成 canonical、Open Graph URL 与 sitemap。域名未知则省略这些绝对 URL，报告未完成项，不填假域名。结构化数据必须与可见内容一致。
- 资源路径适配根页面与子页面；公开文件与 `.site-audit/` 分离。记录公开文件清单，不把源代码证据、本地绝对路径、配置、凭据或审计材料打包进网站。

## 本地验证与交付

读取 [references/validation.md](references/validation.md)，执行与实际网站匹配的本地检查。修复断链、资源缺失、构建失败和可复现交互问题；保留范围明确的业务例外记录，不关闭整类检查来凑通过。

运行本 Skill 的 `scripts/validate_site.py --site <实际公开目录>`，将 JSON 结果保存到公开目录外。脚本仅覆盖静态检查，不能替代浏览器验收。

在审计目录的 `validation.md` 记录命令、结果、功能事实与资源来源、待确认项、未执行的浏览器检查；区分生成完成、本地验证通过与可发布状态。

汇报输出目录、入口、实现页面、使用资源、验证结果和限制，并给出可运行的本地预览方式。不要把静态服务启动成功等同于视觉或功能通过。

## 授权边界

- 创建官网不代表授权发布、上传、搜索引擎提交或修改外部服务；仅用户明确要求时执行这些操作。
- 验证脚本默认本地使用，不自动创建或启用 GitHub Actions。明确要求配置 CI 但未要求自动触发时，只用 workflow_dispatch；已有工作流保持原配置。
- 不自动生成 ASO、广告素材或完整营销包；仅在用户明确要求时扩展。
