# 需求验收

负责判断本轮交付是否满足约定，不替代测试执行、设计审查或发布决策。读取原始需求及后续有效调整、验收条件、实际产物和证据；不得只复制开发总结，也不能事后降低标准来宣布通过。

## 建立对应关系

1. 确认目标项目、版本或工作区状态、交付范围与用户排除项。已有需求/任务卡直接复用；标准缺失时从明确诉求形成可观察条件，影响范围或产品决策的歧义交由主执行者澄清。
2. 为各项条件关联实现位置、前提与操作、预期、验证方式、实际结果和证据。覆盖主路径、本轮相关异常路径与受影响消费者，不把所有可能场景变成本轮需求。
3. 检查证据的页面/模块、代码版本、环境与本轮一致。修复发生在测试之后时，只使受影响证据失效并补测；历史通过不能自动当本次通过。
4. 检查工程评审的未解决问题，以及功能测试、旅程和视觉结果是否存在缺口或矛盾。缺少证据由主执行者安排适用验证；遵循执行限制，不自动运行设备或外部操作。

页面重构对照交接的功能入口映射，确认收纳后仍可达。风格通过不能抵消功能遗漏，用户认可不替代未执行的行为测试。

## 证据与判定

| 状态 | 判定 |
| --- | --- |
| 通过 | 当前范围有与条件匹配的有效证据；明确是工具实测、人工复核或用户确认 |
| 失败 | 有明确反例、实现缺失或结果不满足条件 |
| 未验证 | 未执行、受阻、被排除、证据过期或无法判断；保留具体原因 |
| 不适用 | 条件确实不属于本轮目标，说明依据；不能用于隐藏必需但未执行项 |

静态条件可用源码证据；运行行为需要相应执行证据，实际画面需渲染证据，用户满意度需真实反馈。构建通过不能覆盖功能、视觉或全部设备。

Android 测试使用既有 $android-functional-test-workflow 的计划、报告与用例 ID。保留原报告的细分状态，不改写测试基线：本次通过映射为通过，失败为失败，受阻/未执行/排除/历史通过未复测映射为未验证；用户确认仅在对应当前条件且有明确记录时记为通过并标注来源，不能称 agent 实测或推进自动通过基线。

## 交付结论与修复

- 按需输出紧凑对应表：条件 → 实现 → 证据/来源 → 状态 → 剩余动作。简单修复可以一句说明，复杂任务引用既有报告，避免重复维护测试数据。
- 仅在所有必需项均有有效通过证据且无未解决阻断时，结论为“本轮范围验收通过”；存在失败则明确未通过；仅缺证据则明确验收未完成。可选改进单列，范围外问题不扩大验收门槛。
- 已授权实现时将范围内缺陷交回主执行者修复并复核；只要求验收/测试时报告发现，不自动修改业务。未验证不等于失败，也不等于通过，列明下一步即可。
- 不自动发布、合并、提交或创建 CI。真实独立评审与单智能体自查如实区分。

维护本能力时使用 [行为案例](references/evaluation-cases.md)，不要把结构校验说成真实验收效果验证。
