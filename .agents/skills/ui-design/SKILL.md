# UI 设计师：结构、交互与设计交接

负责把目标转为可实现的页面设计，并检查实际效果。先读取目标项目的适用 UI 规则、相关页面和资源；Android 使用原生组件及项目规范。技术实现由平台实现能力负责，主执行者统一调度，避免相互调用形成循环。

本能力是设计主责：确定用户任务、信息架构、布局、主次操作和状态。风格约束由项目规则维护，$ui-style-review 检查一致性，Android 工作流负责实现。主执行者可以顺序使用这些视角，不代表独立设计师已评审，也不自动授权子智能体。

Android 新页面交互未定、多步骤流程、导航/弹层/返回变化、UX 重构或设计稿平台映射时，使用 [交互专项](../android-interaction-design/SKILL.md) 补齐行为决策。先复用架构能力核实的 Base/组件映射，再形成可实现方案；交互结论合入同一设计交接，已有完整方案只补缺口。导航选择由目标架构规则约束。

## 选择任务分支

- **设计稿还原**：以用户指定版本、节点、图层与资产为依据，复用 Figma/Zeplin 已有任务卡。补齐必要的状态和平台映射，记录差异，不擅自重新设计或静默替换素材。
- **已有页面改进**：先定位用户问题及画面证据，指出应保留的有效设计；只调整与目标有关的层级、密度、操作或视觉规则，不默认整页重建。
- **从零设计**：明确用户、主任务、内容密度和产品气质，结合现有品牌与组件选择一个有理由的方向。确有关键风格分歧时再给简短备选；一般不要求用户逐项批准颜色和间距。
- **仅审查**：输出具体发现和建议，不自动实施。小范围改动仅检查受影响区域及相邻关系。

## 设计输入与交付

复用需求说明中的目标、范围和验收条件。缺失且影响方向时由主执行者采用需求澄清能力；可逆细节说明假设后推进。读取目标项目的适用风格规则、真实资源与基线。DevLib 工作台参考 [设计基线](../../config/ui-baseline.md)；消费项目建立自己的产品规范，不套用工作台品牌。

实现前按 [设计交接](references/design-handoff.md) 给出必要内容：信息优先级、布局、主次操作、视觉资源映射、状态、适配和验收依据。优先引用现有资源而非维护另一份数值表。复杂页面可用线框或可用工具生成预览，但原型不等于 Android 实际渲染。

页面重构先核对本轮涉及的功能与入口，记录原位置、新位置、操作变化及实现状态。已存在功能不得因“简洁”而消失；尚未实现的需求保留缺口，不用空按钮冒充能力。对照目标项目已有需求清单、任务卡或实际入口，只更新本轮影响条目，不把全部规划自动纳入局部任务；没有全量台账时不强制创建。

DevLib 工作台设计前读取 [风格约束](../../rules/ui-style.md)，以 [基线](../../config/ui-baseline.md) 核实实际资源及认可状态；其他目标项目读取其自身适用规范，缺失时依据真实材料提出暂定方向并标注假设。方案先明确“到达哪里、看什么、做什么、如何结束/返回”，再确定视觉表现；专业信息通过分组或渐进展开收纳，并说明如何发现。复杂导航或重构提供主路径与关键页面线框，简单局部修改保留紧凑说明即可。

设计应说明选择与用户任务的关系：控制密度服务于信息检索，主操作突出服务于完成目标。避免无依据添加渐变、装饰卡片、大标题或营销区；安静实用的工具界面同样可以是明确的设计方向。图标保持一致，图片与字体使用实际可用且来源明确的资源。

## 平台与参考资料

- Android 的组件、尺寸单位、导航、系统栏及适配遵循目标规则；不套用 Apple 的 pt、SF Symbols 或平台专属交互。
- 按问题选择 [HIG 资料索引](references/hig-lookup.md) 中的参考；跨平台使用前核对 [适用范围](references/cross-platform.md)。保留的 HIG 资料是历史快照，不代表当前规范已核实。
- 只读取与当前问题有关的资料，不固定加载数量。引用规范必须读过原文；涉及当前版本要求时核对相应官方来源，主观设计判断单独表述。
- 实际颜色、字体和控件尺寸来自代码或设计数据；截图估测注明限制，不编造对比度或尺寸。交互行为不能仅靠静态截图判定。

## 实现交接与视觉闭环

设计说明交给目标平台实现能力；Android 使用 $android-ui-workflow。若现有组件无法满足设计，列出具体差异、成本和可行替代，由主执行者在范围内取舍，不借设计重写基础框架。

实现后按 [视觉验收](references/visual-review.md) 对照实际画面，先修正结构和可读性，再处理细节。$ui-style-review 消费同一方案检查风格；用户操作路径由 $review-user-journey 方法审查，共享问题清单，不重复报告同一问题。发现设计缺陷时更新原交接，不让实现自行换一套设计。

已授权实现任务继续修复范围内问题并复核。没有新证据或受环境限制时停止无效迭代，明确未验证项；不能把编译通过、设计预览或角色自评说成最终视觉通过。

## 能力维护

修改本能力后用 [行为案例](references/evaluation-cases.md) 检查分支和交付；真实任务结果与人工推演分开记录，不能以结构检查替代行为评估。
