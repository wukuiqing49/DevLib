# 视觉验收与修复

## 证据准备

先核对目标项目执行策略与用户排除项，使用允许且可用的渲染/运行途径；禁止为补截图绕过设备限制。记录参考与实际画面的版本、页面、状态、窗口尺寸、主题、语言和字体设置。条件不一致时先解释差异，不能直接归因实现错误。

截图必须来自本轮对应实现；旧图、设计稿、HTML 原型只能作为参考。没有实际渲染证据时可做源码检查并交付待验收项，不能宣称视觉通过。

## 对照顺序

1. 页面目标与信息层级：主操作是否明确，重点内容是否被装饰淹没。
   对照功能入口映射，核查迁移、折叠、菜单收纳后的入口仍可发现；截图不足以证明可操作，流程结果引用实际执行证据。
2. 布局：区域比例、对齐、分组、留白、滚动及固定操作区关系。
3. 可读性：文字层级、真实内容长度、图标语义、颜色和背景关系。
4. 一致性：相邻页面、组件状态与项目资源是否一致。
   使用 ui-style-review 对照目标风格规则；旧页面仅作现状证据，不以一致为理由延续已知问题。
5. 本轮相关的空态、失败、加载及适配场景：按项目 UI 规则选择证据矩阵，未覆盖场景列明。

有设计稿时对照同一版本，必要时使用叠图或并排图；像素差异受字体与平台渲染影响，不能用单一相似度代表可用性。无设计稿时依据已确定的设计说明和项目基线验收，不事后改标准掩盖问题。

## 问题闭环

每项记录：位置/状态 → 观察证据 → 用户影响 → 具体修复 → 复核结果。区分阻断/明显影响/可选打磨，不将个人偏好标为阻断。与旅程审查共用条目。

修复后只复核受影响区域与相关状态；通过且没有新变化时停止重复检查。缺少证据或外部条件时记录原因与下一步，不无限美化。

最终分别报告源码、构建、实际运行、视觉对照的通过/失败/未验证状态；截图不能证明点击、恢复和屏幕阅读器行为，模拟用户不能代替真实用户反馈。
