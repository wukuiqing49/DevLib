# 行为验证案例

维护 Skills 时用以下任务检查路由和结果。优先使用固定输入材料及相同代码基线，在隔离临时目录试验；不自动改生产页面或执行设备命令。独立智能体评估需已有委派授权，否则明确是主执行者人工推演。

| 输入场景 | 可观察预期 | 失败信号 |
| --- | --- | --- |
| “这个工具首页太乱，优化一下”并给现有页面 | 定位用户目标与信息层级，复用资源，提出具体改动与验收 | 未查页面就整页重写，输出空泛美学口号 |
| 给定完整 Figma 任务卡要求还原 | 复用节点、资源、映射，记录平台差异 | 另做风格设计或静默替换资产 |
| 新增工具页，无设计稿 | 提出有理由的方向、布局、真实内容与状态方案 | 只写 XML 或无理由套营销模板 |
| 修复按钮文案溢出 | 检查相关布局与语言，做局部修复 | 启动全量产品策划或改主题 |
| 纯库接口错误处理 | 开发者调用/错误恢复检查，按需旅程审查 | 要求页面、配色和截图 |
| 禁止 adb，只有源码 | 提供静态证据及未验证清单 | 绕过限制或声称视觉通过 |
| 用户只要求 UI 审查 | 交付有证据的问题和建议 | 自动修改业务代码 |
| “首页精简，但所有功能都保留” | 记录原入口与新入口，检查可发现性与关键步骤；低频项有明确去向 | 删除能力或把全部操作放入不可发现的更多菜单 |
| 指定稿与项目旧配色不同 | 以用户指定版本为依据，记录实际平台/风格冲突与处理 | 强行沿用旧页面或另出竞争方案 |
| 当前页面遭用户否定但资源已存在 | 资源为实现事实，设计目标另行确定；不将旧截图升级为认可标准 | 用“保持一致”拒绝修正已知设计问题 |
| “按 Apple Skill 优化 Android” | 读取可用 Apple Skill，将适用发现合并；Android 组件和交互优先 | 复制 iOS 单位/图标/导航，或生成两套互相竞争方案 |
| 只检查组件配色一致性 | ui-style-review 检查实际资源和证据，不重做信息架构 | 要求全面需求分析、重构或新增审批 |
| 普通工具 App 新增有输入的页面，已有 Base 无 Router | 按需使用交互专项，在同一交接中映射 Base/弹窗及简单导航，说明取消和恢复 | 强制路由框架、替换基础组件或输出重复设计报告 |
| 大型模块化 App 调整统一导航入口 | 复用架构调查和交互专项，保留契约，记录参数、返回和恢复 | 只改视觉，或为简化而删除已有路由 |

真实前后对比记录：输入与版本、使用的能力版本、遗漏的需求、返工轮次、具体视觉问题、验证覆盖、耗时及用户反馈。避免仅用输出长度、角色数量或模型自评分判断质量。

本轮结构校验和上述案例人工推演不能称为真实效果对比。后续首次执行真实页面任务时保留对应证据，再依据实际失败修订方法；不为假设问题无限增加硬规则。
