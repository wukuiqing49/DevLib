# Android 交互设计

作为 ui-design 主导方案中的 Android 交互专项，补齐操作与状态决策。主执行者统筹设计、架构和实现，复用同一份任务说明；不另起竞争方案、重复报告或循环调用 Skills。

## 适用范围

- 新页面的操作方式尚未确定，或新增多步骤流程、改变导航/弹层/返回行为时使用。
- UX 重构、设计稿转 Android 涉及交互差异时使用；已有完整任务卡只补缺口，不重设计用户指定稿。
- 明确要求交互审查时只交付发现；已授权实现则将决策交接实现并继续。
- 颜色、文字、图标、局部间距与纯引擎/构建任务不触发完整流程；状态数量、页面数量不单独构成触发条件。

## 输入与基础能力核实

先读取目标项目适用的 AGENTS.md、架构/UI 规则及用户指定设计材料。跨项目缺少同类规则时从实际构建与源码核实，不能直接套用 DevLib 品牌、模块布局或依赖。

复用上游架构调查；缺少时按 [架构能力](../android-project-architecture-workflow/SKILL.md) 的能力映射方法核实本次涉及的 Base、ViewModel、Adapter、弹窗、导航和工具 API。DevLib 使用现有 WKQ 基础能力；已有源码调用是证据，库名称或 README 描述不能证明某 API 可用。只调查当前需要的能力，不要求把全部基础库接入宿主。

导航架构按目标项目的架构规则选择；DevLib 的政策见 [导航与路由选型](../../rules/architecture.md)。交互交接记录选型依据及现有契约，具体依赖与迁移由架构能力评估。本 Skill 单独迁入其他项目且缺少规则时，先核实实际导航与需求，采用能满足任务的最小方案。

## 决策方法

1. 明确用户目标、入口、主操作、完成条件，以及本次相关的取消/返回/失败路径；复用已确认需求。
2. 结合操作依赖、内容长度、窗口空间和既有架构选择内联、弹层或页面；复杂选型读取 [交互模式](references/interaction-patterns.md)。不按固定字段数或步骤数强制组件，不因调用相机/权限自动新增 Activity。
3. 明确状态与恢复：输入/选择由谁持有，提交如何避免重复，离开是否取消，失败如何重试，页面重建如何恢复。需要长期保留的草稿由现有持久化能力承接，不能只声明“放 ViewModel”。只补本轮相关状态。
4. 映射到已核实的组件和资源：具体 Base、Adapter、XPopup/已有弹窗、导航方式、功能库及代码位置。基础组件缺能力时说明差异、可用扩展点和最小替代，不为交互设计另建基础框架。
5. 定义有用途的反馈和动效：让用户知道操作是否生效、是否可取消、下一步是什么；考虑减少动效、焦点、读屏、键盘、触控区域及 RTL。主操作位置根据窗口和输入方式选择，不固定为屏幕下方某个比例。
6. 将决策合入 [设计交接](../ui-design/references/design-handoff.md)。局部任务在对话中简述；复杂任务沿用原任务文档。保留原功能入口映射、用户指定稿差异和可观察验收条件。

## 实现与复核

android-ui-workflow 消费交接，负责 XML + ViewBinding + MVVM、基础库复用、国际化以及系统栏/IME/窗口状态恢复。交互方案注明窗口与内容关系，实现者核实唯一 Insets owner，避免重复设置 Base 已有能力。

review-user-journey 依据同一任务路径复核实际产物；ui-style-review 检查风格，acceptance-review 汇总有效证据。发现问题更新原交接与共享问题清单，不重新启动整套设计。只有源码时仅作静态判断；不自动执行设备操作，也不把编译或原型当作交互已通过。

维护时使用 [行为案例](references/evaluation-cases.md)，区分人工推演、实际执行及真实用户反馈。
