# 交互模式与选择依据

本文件用于存在选型分歧的任务。以下为判断方法；目标项目架构与 UI 规则决定组件映射，用户指定设计的调整必须记录差异。

## 容器、导航与弹层

| 场景 | 选择依据 | 基础能力映射与边界 |
| --- | --- | --- |
| 列表、复杂详情 | 内容是否增长、需要回收或增量更新；简单固定内容可滚动布局，复杂详情也可列表 | 复用 Base Adapter；先核实其更新 API，不强制换成 ListAdapter |
| 平级分类 | 分类之间能否独立浏览、是否保留各自状态；筛选不一定需要子页面 | DevLib 按 UI 规则复用 MagicIndicator/ViewPager2 和已有子 Fragment；外部项目沿用自身组件 |
| 顺序步骤 | 是否需要校验、跳步、草稿、返回前一步；可用已有分页或导航实现 | 复用 Base 页面及 ViewModel；不将 ViewPager2 作为所有向导的唯一实现 |
| 辅助信息 | 是否可内联展开且不打断主任务 | 使用现有布局与状态；展开后考虑焦点及滚动位置 |
| 短选择或输入 | 是否需要保留上下文，键盘出现后是否仍可完成，内容能否合理滚动 | DevLib 优先 XPopup/既有弹窗；允许按需求使用输入对话框，不按输入项数量硬分流 |
| 独立任务与详情 | 独立返回语义、生命周期、外部入口和目标现有页面架构 | 复用对应 BaseActivity/BaseFragment；普通详情可沿用已有 Activity，不为统一形式迁移 |
| 全屏预览与硬件调用 | 是否真正需要独立窗口、沉浸式和独立结果返回 | 优先已有 Base 全屏/预览能力；权限或硬件调用本身不强制新建 Activity |
| 图片与对比 | 同时可见还是顺序查看，窗口空间、图片比例和可读性 | 网格、分页、分屏按实际内容选择；需同时对比时不能仅用左右分页代替 |

页面导航实现与交互形态分别判断：依据目标架构规则与已有导航契约映射页面和参数，库 API 不因 Demo 的导航选型而增加宿主框架依赖。

## 反馈、恢复与安全操作

- 字段错误优先贴近字段反馈，提交时聚焦首个错误；重试提示应位于用户可见且可行动的位置。短暂可恢复错误可使用非阻塞反馈，不把全部错误强制变成 Dialog。
- 删除前先确定是否真实可恢复。可恢复删除可提供撤销并明确恢复范围；不可恢复操作先确认具体后果，不显示无法兑现的 Undo。撤销时限、后台完成及进程重建按实际数据契约设计。
- 长任务明确进度是否可测、取消是否生效、离开页面是否继续、完成产物在哪里。复用现有任务/功能库状态；加载占位、进度条或骨架按场景选择，不为每个请求引入骨架依赖。
- 草稿、选择、滚动位置和进行中任务分开定义恢复策略；区分窗口重建、进程重建和用户再次打开。不把所有状态一律持久化，也不让恢复重复触发提交。
- 动效服务状态与空间关系，时长依任务和项目规范确定。先复用已有反馈/系统组件，检查减少动效行为；不统一强加缩放、共享元素或 300ms 上限，不重复叠加系统动效缩放。
- 主操作位置兼顾单手、键盘、横屏和大窗口；触控区域与图形尺寸分开，沿用项目可访问性要求。错误和选择状态不只靠颜色，弹层关闭后恢复合理焦点。

## 组件不足时

先检查实际公开 API、已有调用和扩展点，记录“交互需求 → 现有能力 → 缺口 → 最小方案”。局部宿主编排留在 feature；可独立复用能力才评估进入 core。不得把消费产品业务、权限 UI 或付费策略放入基础库，也不修改未涉及的基础实现。
